## 3. 附件1的数据结构

`data/附件1.xlsx` 当前只有一个工作表，共 145 行、4 列：

| 列 | 字段 | 单位 |
|---|---|---|
| A | 时间 | - |
| B | 电价 | 元/kWh |
| C | 小区负载 | kW |
| D | 光伏发电预测功率 | kW |

第 1 行为表头，第 2～145 行为 144 个时间点的数据。

因此：

```text
T = 144
```

每个调度时间步长度：

\[
\Delta t = 10\text{ min}=\frac{1}{6}\text{ h}
\]

输入的小区负载和光伏数据都是功率 `kW`，而模型的购电量、充电量、放电量均采用能量 `kWh`，因此必须先进行转换：

\[
L_t = P^{load}_t\Delta t
\]

\[
PV_t=P^{pv}_t\Delta t
\]

即代码中：

```python
load_kwh = load_kw / 6.0
pv_kwh = pv_kw / 6.0
```

电价本身已经是：

```text
元/kWh
```

因此无需进行时间换算。

### 3.1 时间行的处理原则

不要对附件1按照时间字符串重新排序。

必须保持附件1原始 144 行的顺序，将其视为：

```text
slot 0
slot 1
...
slot 143
```

即 144 个连续的 10 分钟调度时间步。

官方 `result1.xlsx` 模板中的“计划购电量”工作表也正好有 144 个待填结果行，因此输出时采用**严格按行号一一对应**的方式，不重新生成时间段标签。

附件1与结果模板在日界附近的时间标签存在容易产生歧义的写法，因此程序内部一律以 `slot_index=0..143` 作为调度主索引，不允许以时间字符串作为模型数组下标。

## 4. 储能设备参数

根据题目附录，固定参数如下：

```python
BATTERY_CAPACITY_KWH = 12000.0
SOC_MIN_KWH = 1200.0
SOC_MAX_KWH = 10800.0

BATTERY_POWER_MAX_KW = 5000.0

ETA_CHARGE = 0.90
ETA_DISCHARGE = 0.90

INITIAL_SOC_KWH = 6000.0
FINAL_SOC_KWH = 6000.0
```

因为一个时间步为 10 分钟，所以单个时间步最大充电量和最大放电量均为：

\[
E^{max}
=
5000\times\frac{1}{6}
=
833.333333\text{ kWh}
\]

代码中：

```python
BATTERY_ENERGY_MAX_PER_SLOT_KWH = BATTERY_POWER_MAX_KW / 6.0
```

### 4.1 效率定义

本文档采用如下统一约定：

- `charge[t]`：微网交流侧送入储能设备的电量；
- `discharge[t]`：储能设备向微网交流侧输出的电量；
- 充电效率为 0.9；
- 放电效率为 0.9。

因此 SOC 更新方程为：

\[
SOC_t
=
SOC_{t-1}
+
0.9C_t
-
\frac{D_t}{0.9}
\]

不要写成：

\[
SOC_t=SOC_{t-1}+0.9C_t-0.9D_t
\]

后者代表了不同的物理定义，会导致结果发生变化。

## 5. 问题1的线性规划模型

### 5.1 决策变量

对于每一个时间步：

\[
t=1,2,\ldots,144
\]

定义：

\[
G_t\ge 0
\]

表示第 \(t\) 个时间步从外部电网计划购买的电量，单位 `kWh`。

\[
C_t\ge0
\]

表示第 \(t\) 个时间步储能充电量，单位 `kWh`。

\[
D_t\ge0
\]

表示第 \(t\) 个时间步储能放电量，单位 `kWh`。

\[
W_t\ge0
\]

表示未被负载或储能利用的剩余光伏电量，即弃光量，单位 `kWh`。

\[
SOC_t
\]

表示第 \(t\) 个时间步结束后的储电量，单位 `kWh`。

### 5.2 为什么需要弃光变量

如果某一时段：

```text
光伏发电 > 小区负载 + 储能当前可充电能力
```

则多余的光伏必须允许被舍弃，否则电量平衡等式可能无解。

因此加入：

\[
W_t\ge0
\]

可以使模型在任何合理光伏输入下保持物理可行性。

问题1不存在向外部电网售电，因此：

```text
W_t 只能表示弃光，不能产生收入。
```

## 6. 目标函数

题目要求最小化购电费用：

\[
\min
\sum_{t=1}^{144}q_tG_t
\]

其中：

- \(q_t\)：附件1给出的电价；
- \(G_t\)：计划购电量。

为了避免在线性规划存在多个经济成本完全相同的最优解时，求解器给出“同一时段同时充电和放电”的退化解，在求解器内部加入极小的储能吞吐量惩罚：

\[
\min
\left[
\sum_{t=1}^{144}q_tG_t
+
\varepsilon\sum_{t=1}^{144}(C_t+D_t)
\right]
\]

推荐：

```python
EPS_THROUGHPUT = 1e-8
```

该项仅用于打破 LP 的退化解。

### 6.1 正式购电费的计算

最终论文和程序输出的“全天购电费”必须重新按照：

```python
total_cost = np.dot(price, grid_purchase)
```

计算。

不要使用 `linprog` 返回的完整目标函数值作为正式购电费，因为完整目标函数中含有极小的 `EPS_THROUGHPUT` 辅助项。

## 7. 约束条件

### 7.1 电量平衡约束

对于每个时间步：

\[
G_t+PV_t+D_t
=
L_t+C_t+W_t
\]

等价写成：

\[
G_t-C_t+D_t-W_t=L_t-PV_t
\]

其中：

- \(PV_t\)：光伏发电预测功率换算得到的 10 分钟电量；
- \(L_t\)：小区负载功率换算得到的 10 分钟电量。

该约束保证微网始终满足负载。

不要简单写：

\[
G_t+PV_t+D_t\ge L_t
\]

因为充电过程本身也会消耗电能，必须放在完整的系统能量平衡中统一建模。

---

### 7.2 SOC 动态约束

第一个时间步：

\[
SOC_1
=
6000
+
0.9C_1
-
\frac{D_1}{0.9}
\]

其余时间步：

\[
SOC_t
=
SOC_{t-1}
+
0.9C_t
-
\frac{D_t}{0.9}
\]

---

### 7.3 SOC 上下界

所有时间步结束后均满足：

\[
1200\le SOC_t\le10800
\]

---

### 7.4 充放电功率约束

由于最大充放电功率为 5000 kW：

\[
0\le C_t\le833.333333
\]

\[
0\le D_t\le833.333333
\]

---

### 7.5 日初日末储电量约束

问题1要求：

\[
SOC_{0:00}=SOC_{24:00}
\]

本文档根据附录给出的初始储电量统一取：

\[
SOC_{0:00}=6000
\]

因此同时约束：

\[
SOC_{24:00}=6000
\]

即：

```python
INITIAL_SOC_KWH = 6000.0
FINAL_SOC_KWH = 6000.0
```

## 8. 是否需要“禁止同时充放电”的二元变量

问题1不推荐为此引入 MILP 二元变量。

理论上可以定义：

\[
z_t\in\{0,1\}
\]

然后限制：

\[
C_t\le E^{max}z_t
\]

\[
D_t\le E^{max}(1-z_t)
\]

但这会把问题从 LP 变为 MILP，没有必要。

问题1使用：

```text
LP + 极小吞吐量惩罚
```

即可避免没有经济意义的同时充放电解。

程序完成后仍需验证：

```python
np.any((charge > tol) & (discharge > tol))
```

正常结果应为 `False`。

## 9. SciPy `linprog` 的变量组织

建议将全部决策变量拼成一个一维向量：

\[
x=
[
G_1,\ldots,G_T,\;
C_1,\ldots,C_T,\;
D_1,\ldots,D_T,\;
W_1,\ldots,W_T,\;
SOC_1,\ldots,SOC_T
]^T
\]

其中：

```python
T = 144
N_VAR = 5 * T
```

Python 下标建议固定为：

```python
GRID_START = 0
CHARGE_START = T
DISCHARGE_START = 2 * T
CURTAIL_START = 3 * T
SOC_START = 4 * T
```

封装索引函数：

```python
def idx_grid(t: int) -> int:
    return t

def idx_charge(t: int) -> int:
    return T + t

def idx_discharge(t: int) -> int:
    return 2 * T + t

def idx_curtail(t: int) -> int:
    return 3 * T + t

def idx_soc(t: int) -> int:
    return 4 * T + t
```

不要在模型构造代码中大量手写 `2*T+t`、`4*T+t`，以免后续修改时出现错位。

## 10. `linprog` 目标系数

初始化：

```python
c = np.zeros(5 * T, dtype=float)
```

购电变量：

```python
c[0:T] = price
```

充电变量：

```python
c[T:2*T] = EPS_THROUGHPUT
```

放电变量：

```python
c[2*T:3*T] = EPS_THROUGHPUT
```

弃光和 SOC 的目标系数均为 0。

## 11. 等式约束矩阵

推荐使用：

```python
scipy.sparse.lil_matrix
```

构造约束矩阵，最终转成 CSR。

### 11.1 电量平衡约束

共 144 行。

每一行满足：

```text
+1 * grid[t]
-1 * charge[t]
+1 * discharge[t]
-1 * curtail[t]
=
load_kwh[t] - pv_kwh[t]
```

---

### 11.2 SOC 动态约束

共 144 行。

`t == 0`：

```text
soc[0]
- ETA_CHARGE * charge[0]
+ discharge[0] / ETA_DISCHARGE
=
INITIAL_SOC_KWH
```

`t > 0`：

```text
soc[t]
- soc[t-1]
- ETA_CHARGE * charge[t]
+ discharge[t] / ETA_DISCHARGE
=
0
```

---

### 11.3 终端 SOC 约束

再增加 1 行：

```text
soc[143] = FINAL_SOC_KWH
```

因此总等式约束数量：

```python
N_EQ = 144 + 144 + 1
     = 289
```

## 19. 独立结果校验公式

### 19.1 电量平衡

程序完成求解后重新计算：

```python
balance_residual = (
    grid_purchase_kwh
    + pv_kwh
    + discharge_kwh
    - load_kwh
    - charge_kwh
    - curtailment_kwh
)
```

要求：

```python
np.max(np.abs(balance_residual)) <= 1e-5
```

---

### 19.2 SOC 动态

建议独立从初始 SOC 重建：

```python
soc_reconstructed = np.empty(144)

prev = INITIAL_SOC_KWH

for t in range(144):
    current = (
        prev
        + ETA_CHARGE * charge_kwh[t]
        - discharge_kwh[t] / ETA_DISCHARGE
    )

    soc_reconstructed[t] = current
    prev = current
```

要求：

```python
np.max(
    np.abs(soc_reconstructed - soc_end_kwh)
) <= 1e-5
```

---

### 19.3 SOC 范围

```python
soc_end_kwh.min() >= SOC_MIN_KWH - TOL
soc_end_kwh.max() <= SOC_MAX_KWH + TOL
```

---

### 19.4 终端 SOC

```python
abs(soc_end_kwh[-1] - FINAL_SOC_KWH) <= 1e-5
```

---

### 19.5 充放电上限

```python
charge_kwh.max() <= 833.3333333333334 + TOL
discharge_kwh.max() <= 833.3333333333334 + TOL
```

---

### 19.6 同时充放电检查

```python
simultaneous = (
    (charge_kwh > 1e-5)
    & (discharge_kwh > 1e-5)
)
```

正常情况下：

```python
simultaneous.sum() == 0
```

如果出现同时充放电，程序可先记录警告；如果数量较多，则视为模型实现存在问题。
